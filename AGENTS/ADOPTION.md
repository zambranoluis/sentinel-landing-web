# Adopting the neutral standard

The neutral source is a template, not an active project installation. Keep its nine-file structure: the five instruction files (AGENTS.md, AGENTS/INVESTIGATIONS.md, AGENTS/FRONTEND_CREATION.md, AGENTS/PLANS.md, AGENTS/CODE.md), the unconfigured root README.md, PRODUCT.md, and DESIGN.md starters, and this permanent AGENTS/ADOPTION.md with its conditional entry routing from AGENTS.md. Keep the canonical neutral version separate from project adaptations.

Every project adoption includes AGENTS/FRONTEND_CREATION.md, plus a temporary project AGENTS/ADOPTION.md and entry link while assimilation is active. Install the frontend process even where its trigger does not apply to current work; read it only when routed by AGENTS.md. Reconcile the intended repository before materializing or merging documents. Require root README.md, PRODUCT.md, and DESIGN.md. After retirement, the five instruction files and project documents work independently. Make installed guidance available to collaborators and hosted agents when they need it; local ignored files do not provide shared guidance.

## Reconcile before claiming adoption

For an empty project, establish applicable requirements and initial choices without inventing existing conventions. For an existing project, reconcile its instructions and decisions before installation; preserve applicable guidance before replacing any instruction file.

1. **Inventory:** Read existing instructions, user direction, root and detailed product/design/architecture documents, source layout, contracts, scripts, tests, tools, and known debt. Read the sources that own material claims; mark absent or unresolved sources explicitly. Establish which design concerns apply and identify the intended hosts. For an instruction upgrade, inventory any existing root ADOPTION.md and AGENTS/ADOPTION.md, including their decisions, evidence, and unrelated content.
2. **Classify and resolve:** Classify each candidate rule as portable, project-specific, framework-specific, host-specific, temporary, or obsolete. Resolve conflicts against actual project requirements and host instruction priority. Implementation establishes observed behavior, not automatically the intended contract. Retain supported conventions, identify debt and inconsistencies, and resolve material disagreement with the responsible owner before dependent changes under [INVESTIGATIONS.md](INVESTIGATIONS.md#evidence-and-boundaries); unrelated remediation is not an adoption requirement. Record unresolved choices, owners, and the work they block. Use [CODE.md](CODE.md#starting-preferences) per concern where a convention is missing in a new or existing project. Select only relevant framework or tool procedures. Where material product or design gaps remain, use the conditional capability offer below before dependent reconciliation.
3. **Materialize or merge:** Within authorized adoption implementation, install or merge the five instruction files, required root project documents, and a temporary project AGENTS/ADOPTION.md. Preserve existing README, PRODUCT, and DESIGN content. Where another source already owns detailed product or design guidance, make the required root document a concise entry to that owner rather than copying its rules. Where ownership is missing, materialize the starter and populate only verified facts and settled decisions. Keep unknowns with owners and blocked work; neither a starter nor an implementation observation approves a requirement. Record operational context and the selected stack in [README.md](../README.md), product truth in [PRODUCT.md](../PRODUCT.md), applicable design requirements in [DESIGN.md](../DESIGN.md), and engineering decisions, rationale, package approvals, contracts, and debt ownership in [CODE.md](CODE.md#project-engineering-guidance) or its linked owners. Reconcile incrementally even while the application is incomplete. Documentation maintenance does not authorize an unapproved migration, dependency, or new product decision.

   If PRODUCT.md or DESIGN.md is absent, offer to create each missing document using its applicable available Impeccable workflow under [Conditional capability offer](#conditional-capability-offer) before materializing a starter. If both are absent, settle the product context before a pre-implementation design seed. Use each resulting document when its workflow is selected and its required direction is settled; otherwise install its root starter or an entry to an established owner. Record verified facts and settled decisions only; mark unresolved direction or inapplicable concerns explicitly rather than inventing requirements. Preserve existing PRODUCT and DESIGN content and resolve their ownership rather than replacing either as a side effect.

   Adapt the temporary guide to supply the applicable reconciliation procedure, scope, intended hosts, current state, last reconciliation date, assimilation decisions, open adoption work and owners, required checks, blockers, next action, and retirement criteria, either directly or through its referenced execution record. It supplies no enduring product or engineering authority. Retain the conditional adoption paragraph and link from the installed root AGENTS.md to AGENTS/ADOPTION.md while assimilation is active; remove them only when the retirement criteria below pass. Keep this routing permanently in the canonical neutral entry file. If an existing guide contains lasting or unrelated material, preserve it and resolve its ownership and permitted destination before replacement or removal. For a future upgrade from a profile-based installation, preserve lasting and unrelated profile content in appropriate permitted owners or records before retiring the old file; reconcile against local decisions rather than replacing them blindly. This source revision does not upgrade another repository.

   For a future upgrade with a root ADOPTION.md, preserve its decisions, evidence, and unrelated content before relocating it to AGENTS/ADOPTION.md. If both locations exist, reconcile their contents and resolve material conflicts with the responsible owner before replacing either guide. Correct the relocated guide's relative links and update active references within the authorized project boundary. Remove the root guide only after its content has been preserved or reconciled.

   Add links only to real documents agents should read on demand. Inspect tracking, privacy, and artifact policy before claiming installed guidance or work records are shared. Keep host adapters and configuration with their actual owner; adoption does not authorize capability installation or configuration.
4. **Verify:** Check every local Markdown target and heading anchor, claims against their owners, and applicable commands and prerequisites. Verify discovery and actual loading in each intended host. Check a fresh session for the entry point, routed documents, and representative task behavior; filename presence and Markdown links alone do not prove loading. Trace an answer, a review, an implementation, a UI change if applicable, and a blocked-contract case through the full chain. Check authorization, owner routing, evidence, required decisions, verification, and handoff. Confirm the permanent chain can operate without the guide or its history; correct gaps in the owning document. These host and behavior checks are obligations of each project adoption, not outcomes proved by revising the neutral source.

## Conditional capability offer

When PRODUCT.md or DESIGN.md is missing, or material product or design gaps remain, verify actual Impeccable availability and offer the appropriate installed workflow: `init` to create or complete PRODUCT.md, `document` to create DESIGN.md from an incumbent design system, or `document --seed` for a pre-implementation design direction. Follow the installed skill's current instructions when selected; these workflow names do not freeze its schema or procedure. Preserve existing owners, settle material user decisions before dependent changes, and distinguish observed design from intended requirements.

A starter's presence does not establish complete context capture. An unavailable or declined skill does not block equivalent authorized reconciliation: inspect owning sources, invite decisions on material gaps, and record verified facts, settled choices, and explicit unknowns. Keep skill schemas, sidecars, launchers, hooks, and configuration with their actual owner. Do not install or configure a capability as an adoption side effect or add skill-specific requirements to the neutral starters.

## Completion and retirement

The temporary project AGENTS/ADOPTION.md owns assimilation and retirement; settled project documents own lasting facts and decisions. Keep adoption history and verification evidence in the guide or its referenced execution record while work is active. Before retirement, preserve relevant decisions, verification results and limits, blockers and their resolution, and completion evidence in the adoption work item's compact execution record under [PLANS.md](PLANS.md#location): default `workspace/<adoption-work-item>/plan.md`, with optional substantial evidence under `records/`. Use a different record root only when designated through README. Inspect actual sharing and permitted prerequisites; do not claim records are accessible without checking.

Permanent guidance must stand independently after adoption. Do not add adoption-status sections or mandatory history links to README, PRODUCT, DESIGN, or the core instruction files. Settled decisions remain with their owners; [CODE.md](CODE.md#project-engineering-guidance) and its linked engineering sources retain discoverable ownership of ongoing debt and differences.

Retire the temporary project AGENTS/ADOPTION.md only when all these conditions hold:

1. Applicable existing instructions and project decisions have been reconciled, and material adoption disagreements are resolved.
2. The permanent chain lets a fresh agent find reconciled owners, requirements, contracts, commands, and accessible permitted prerequisites without depending on the temporary guide or its history.
3. Required adoption checks have passed: local links and anchors, source claims, applicable command verification, and fresh-session loading and representative behavior in each intended host.
4. Lasting guidance and permitted evidence have accessible destinations. Remaining product work and known debt have owners and records, with engineering debt routed through CODE.

A required check that cannot run keeps adoption open and AGENTS/ADOPTION.md in place. Record its blocker and exact remaining verification in the guide or its referenced execution record; continue independent authorized work. Future product decisions and unrelated debt do not require a finished application before adoption can complete.

Once these conditions pass, within authorized adoption implementation:

1. Preserve relevant decision history and verification evidence in the adoption work item's compact execution record before removal. Move any lasting guidance held only in the guide to its owner, and resolve the ownership and permitted destination of unrelated material. Keep the record concise under PLANS; it must be usable without the conversation.
2. Remove the temporary project AGENTS/ADOPTION.md and its active references, including the conditional adoption paragraph and link from the installed root AGENTS.md to AGENTS/ADOPTION.md.
3. Check the surviving instruction chain and links, then record completion and its date in the work-item record. If the final check fails, correct the surviving chain before marking completion.

A read-only, review-only, or plan-only request reports findings or readiness without populating project documents or performing adoption cleanup. Saving a requested plan authorizes only that record. Use no calendar expiration or automatic deletion script. Ordinary project-document maintenance after completion does not recreate the guide; a subsequent adoption or instruction upgrade follows a new scoped reconciliation. Never retire the neutral source template's permanent AGENTS/ADOPTION.md.

If an adopted project needs concrete Next.js or other framework guidance, place it in the project's owning engineering documentation and route to it from CODE, with operational entry points in README.

## Host activation

The neutral files make no cross-host precedence claim. The following is a documentation-based activation check as of 2026-10-01, not proof that an installed host loaded these files:

| Host                                                                                       | Check during adoption                                                                                                                                                                                                         |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md)                      | Place the entry file at the intended repository scope; in a fresh session, inspect which instruction sources loaded and read a routed document for a representative task.                                                     |
| [Claude Code](https://code.claude.com/docs/en/memory)                                      | Current versions can read AGENTS.md directly under documented conditions. Check the installed version and any CLAUDE.md or project-instruction setting; use an actual import only when needed, then verify the loaded source. |
| [GitHub Copilot](https://docs.github.com/en/copilot/reference/custom-instructions-support) | Check the exact product surface. AGENTS.md support varies across Chat, agent, review, CLI, and IDE environments; add a minimal supported adapter only for a surface that needs one.                                           |
| [OpenCode V2](https://opencode.ai/v2/docs/instructions)                                    | Verify AGENTS.md loading in a fresh session. V2 does not currently resolve files from its instructions array; nested discovery and updates have their own behavior.                                                           |

Check the installed version and environment before adding any adapter. Do not assume linked Markdown is injected automatically or that a filename proves activation. Test representative behavior in the target host rather than copying a provider-specific claim into the neutral core.
