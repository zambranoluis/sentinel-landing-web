# Frontend creation

This process applies to new interfaces, redesigns, meaningful visual or interaction extensions, and explicit requests for the process or Impeccable. For a narrow correction with settled direction, use only relevant guidance unless the process or Impeccable was explicitly requested. [AGENTS.md](../AGENTS.md) owns authorization, [INVESTIGATIONS.md](INVESTIGATIONS.md) owns grounding and evidence, and [PLANS.md](PLANS.md) owns records and stops. Product and design requirements remain with [PRODUCT.md](../PRODUCT.md) and, when applicable, [DESIGN.md](../DESIGN.md); [CODE.md](CODE.md#verification) owns verification.

## Establish direction

Identify the supplied direction, user job, affected states, and material choices about flow, hierarchy, visual treatment, assets, interaction, and motion. Resolve factual gaps through the owning sources and current behavior. Ask the user when an unresolved preference or tradeoff could materially change the result, and continue independent authorized work while the answer is pending. Review the chosen direction before production work that depends on an unsettled choice.

For meaningful state changes, decide entry, exit, repositioning, and interruption where applicable, including responsive and reduced-motion behavior. Immediate change is valid when animation adds no value.

## Choose skills and examples

Check relevant installed skills and their actual availability. For design work that materially needs Impeccable, or when the user invokes it, use it when available and follow the installed skill's current instructions. Keep provider-specific launchers and configuration with their owner. If a skill is unavailable, use a capable available method; explain a material capability gap and its effect under [INVESTIGATIONS.md](INVESTIGATIONS.md#sufficiency-test).

Use targeted external examples when they would resolve an open design question and access is available. Choose by the question: [Refero](https://refero.design/) for screens and flows; [Refero Styles](https://styles.refero.design/) or [VoltAgent's collection](https://github.com/VoltAgent/awesome-design-md) for visual systems; and [Emil Kowalski's skills](https://github.com/emilkowalski/skills) for focused interaction and motion questions. Other examples may fit better. Inspect live behavior when current flow, motion, or responsiveness matters. Record the pattern considered and its adaptation to this project's requirements or rejection. External examples and skills are research, not project authority or permission to install dependencies.

## Preview when direction remains open

When the user asks to review a preview first, or a material user-facing direction cannot be settled from project guidance and evidence, prepare a reviewable preview in a format the user can actually inspect. An interactive browser preview is the default for unresolved interactive web direction when feasible. Keep its runnable entry and necessary assets together in the work-item record location specified by [PLANS.md](PLANS.md#location). Exercise material interactions and motion before presenting it. State what the preview demonstrates, its entry point, and any behavior it represents rather than reproduces. Obtain the direction decision before dependent production work.

After a meaningful preview revision, re-open the current entry point and check text, assets, interaction, and relevant motion. Label retained alternatives and identify the current one. If the requested preview format is unavailable, explain the limit and offer viable alternatives; a concise brief can settle a choice when a visual preview is unnecessary.

For an existing UI change, compare relevant before and after browser evidence when a relevant lane can run. If that lane is unavailable, apply the [sufficiency test](INVESTIGATIONS.md#sufficiency-test): pause work dependent on necessary observations, or continue sufficiently grounded scoped work with explicit limits. State which behavior or presentation remains unverified and the exact check to run once it is available.
